# 2026-09-07 プロジェクト発足の経緯とスコープ

## 経緯

- 送迎プラン作成サポートの要件定義(v0.6)では、当初「④職員シフト管理機能」というコンポーネントが構想されていた。
- 2026-09-02、送迎プラン作成サポート側で以下が決定され、④はスコープ外となった:
  - 職員シフト管理機能は送迎プラン作成サポート内では開発しない。
  - 送迎プランの職員シフトはAgriCamp等から月次でPDF/画像を取込・手動入力する運用とする。
  - 参照: 送迎プラン作成サポート `code/docs/decisions/2026-09-02-shift-and-usage-plan-sourcing.md`。
- 一方で、シフト作成自体を支援する機能へのニーズ(論点整理は [../../../参考資料/シフト作成に関する回答.pdf](../../../参考資料/シフト作成に関する回答.pdf) 参照)は残っており、2026-09-07、これを**独立したプロジェクト**として発足させることとした。

## スコープ・位置づけ(2026-09-07確定)

- **AgriCampとも送迎プラン作成サポートとも独立したプロジェクト**として `code/` 配下に新規構築する。
  - DB・認証・コードベースは共有しない。
  - AgriCampからは「外部から利用できるコンポーネント」として、API経由でのみ連携する(例: 確定シフトデータの参照)。連携の具体API仕様は今後詳細化する。
- Staff(職員)・Facility(事業所)マスタは、このプロジェクト内にローカルで持つ。送迎プラン作成サポート側のStaffマスタとは連動しない(IDが一致する保証はない。連携が必要になった時点で紐付け方法を別途検討する)。

## 引き継いだ検討材料(参考資料フォルダに実体をコピー)

1. **職員情報マスター登録項目**(氏名・権限設定・職制区分・在籍ステータス・運転可能量区分・電話番号・メールアドレス) — [参考資料/職員情報マスター登録の内容について...txt](../../../参考資料/職員情報マスター登録の内容について以下の項目を登録項目とする改修を行っ.txt)。送迎プラン作成サポート側でも同様の項目でStaffマスタを実装済み(2026-09-02)だが、本プロジェクトでは独立したマスタとして同項目を土台に実装する。
2. **シフト作成に関する残論点**(参考資料/シフト作成に関する回答.pdf):
   - 必要配置人数マスタ: 当日の利用人数により必要人数が変動するルールがある。初期データはExcelからの棚卸しが必要(未着手・要追加ヒアリング)。
   - 法定労働時間などの法令制約: 将来的にスコープへ含め、作成段階で違反を回避するロジックを検討(不必要な残業の抑制)。
   - 職員とLINE公式アカウントの「友だち」紐付け: 職員個人宛のプッシュ通知のため、初回登録リンクで友だち追加+本人特定を行う仕組みが必要(詳細設計時に検討)。
   - 固有リンク(マジックリンク)のセキュリティ設計: トークン有効期限、なりすまし対策。SMSワンタイムパスワードによる2段階認証(またはパスキー)を予定。
   - 職員マスタで就業状態ステータスを管理し、休職・退職者をシステム利用対象から除外する運用を徹底する。
3. **現行の出勤表サンプル**: [参考資料/全員　出勤表R8-9.pdf](../../../参考資料/全員　出勤表R8-9.pdf)(令和8年9月分、全職員・全事業所の実データ形式)。画面設計・データモデル検討時の参考にする。

## 今回のキックオフでやったこと

- プロジェクト一式(server: Express+TypeScript+Prisma、client: React+TypeScript+Vite)の雛形を作成。
- Staff・Facility・RequiredStaffing(必要配置人数)・ShiftAssignment(シフト割当)の初期データモデルを作成(職員情報マスター登録項目 準拠)。
- 外部連携用のAPI(`/api/external/*`)にAPIキー認証の枠だけ用意(実データ・実運用は今後)。

## 未着手・今後の検討事項

- 必要配置人数マスタの「当日利用人数に応じた変動ルール」の実装(現状は曜日別の固定値のみ)。
- 法定労働時間チェックロジック。
- LINE友だち紐付け・個人宛プッシュ通知。
- マジックリンク+SMS OTPによる職員認証。
- AgriCampとの実際の連携仕様(どのデータを・どの粒度で・どちらが正とするか)。
